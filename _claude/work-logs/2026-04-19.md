## User Feedback from First Playtest

### 1. Remove harmonic mode from Tier I
Harmonic (simultaneous) playback doesn't make sense for Tier I pitch discrimination. It should strictly be melodic (sequential, one note after the other). Harmonic mode may belong in Tier II or later, but for same/higher/lower judgment, sequential is the right call.

### 2. Hum-back feature: add guided mode after answering
Current behavior: mic/hum input shows detected pitch with no correctness feedback. This is good for free practice.

Requested addition: after the user answers a pair (higher/lower/same) and gets the result, allow them to hum again with the **second note as a target** — light up green when they've matched it. This creates a two-phase hum experience:
- **Before answer:** free hum, no feedback (as-is)
- **After answer:** guided hum, green light when hitting the target note

### 3. Cello sound quality
Piano sound is good. Cello sound is bad — sounds synth-y, not cello-like.

**Current implementation:** Pure Web Audio API oscillator synthesis (sawtooth wave + filter, bowed attack/release envelope). No libraries, no samples. This is why it sounds synthetic — it's literally a shaped sawtooth wave, not a modeled or sampled cello.

**Alternatives to explore next session:**
- **Sampled audio:** Use actual cello recordings (e.g. short .mp3/.wav per note). Most realistic, but adds file dependencies and breaks the single-file architecture.
- **Tone.js:** Higher-level Web Audio library with better built-in synths and sample player support. Still JS, no build step needed (CDN).
- **AudioKit (iOS only):** Relevant for v4 native app, not web.
- **Improve current synthesis:** Add vibrato, multiple detuned oscillators, formant filtering — can get closer to "stringy" but will never truly sound like a cello.

Decision needed: is breaking the single-file constraint worth it for better cello sound?
